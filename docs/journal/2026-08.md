# Engineering journal — August 2026

## 2026-08-18 — First real LAS forensic and acquisition baseline

### Work performed

Validated the first real Campo Digital LAS and implemented reproducible streaming analysis for:

- observed LAS geometry;
- header/observed bound comparison;
- GPS-time ordering;
- return-number statistics;
- exact timestamp grouping;
- R1/R2 pair geometry.

### Problems encountered

- LAS-header bounds were stale relative to actual point coordinates.
- CRS is absent.
- The file appears to have passed through a `txt2las` export/conversion workflow.
- Incremental implementation patches initially depended too closely on formatter-specific source layout.
- A mypy issue was caused by reusing `dx`, `dy`, and `dz` as both scalar and NumPy-array variables.
- Timestamp groups needed explicit preservation across streaming chunk boundaries.

### Findings

- 9,718,909 real points are readable reproducibly.
- GPS time is non-decreasing.
- 5,609,224 exact timestamp groups exist.
- 4,109,685 groups contain exactly two points.
- Every two-point group is ordered Return 1 -> Return 2.
- No timestamp group contains more than two records.
- Some exact R1/R2 pairs have very large spatial separation.
- The visible timber wall is the next useful geometric target.

### Decisions

- geometry uses observed point bounds;
- original header bounds remain available for audit;
- CRS and linear units are not inferred;
- numeric LAS scale is not treated as physical accuracy;
- raw mesh/voxel volume is not automatically commercial cubicación;
- CloudCompare is used as a visual debugger, not as the authoritative processing workflow;
- generic acquisition forensics should no longer dominate the PoC.

~~~

`docs/es/preguntas-campo-digital.md`

~~~text

~~~

### Depth observability

Multiple methods were used to search for a coherent opposite pile wall:

- transverse density profiles;

## 2026-08-25 — Projected face-area raster kernel (V1)

### Work performed

On branch `feat/gs100g-front-face-area-v1`, implemented a second, independent front-face area estimator alongside the existing scanline cross-section: `src/lidar_volume/projected_face_raster.py`. It orthographically projects an already-isolated pile onto the scanline estimator's own `(u, z)` face frame, rasterizes with density-aware occupancy, rejects small noise components, optionally closes small gaps, keeps the single largest connected component, and fills fully-enclosed internal holes to report a gross projected external silhouette area.

Covered with 17 synthetic NumPy-only tests (rectangular wall, sloped bottom, irregular top, transverse-protrusion invariance, sparse outliers, internal holes, a second non-noise disconnected component, determinism, invalid configuration). Wired into `run_timber_measurement` as a coexisting diagnostic (`MeasurementRun.projected_face_raster`), with two new artifacts (`projected_face_raster.json`, `projected_face_raster.png`) and a scanline-disagreement diagnostic. The existing `front_cross_section` result and `results`/volume computation are unchanged.

Ran an initial, uncommitted, SOURCE-UNIT sensitivity sweep (cell sizes 0.02–0.15) against the frozen `timber_stack_manual_reference_v1.las`. Raster area exceeded the scanline rectangle area at every tested cell size, with disagreement growing from ~7% (finest) to ~15% (coarsest) — consistent with coarse-cell boundary staircasing. See `EXP-006` for full method, numbers, limitations, and open questions.

Ruff/mypy/pytest/doc-link gates all green. Not committed per this session's instructions — see the session report for full file list.


## 2026-08-25 — GS100G boundary-estimator comparison

Campo Digital confirmed that the target quantity is the projected area of the
roadside-facing timber-stack face — specifically the face that can currently
be drawn manually in measurement software and should be automated.

A controlled estimator comparison was performed on the frozen manually
isolated GS100G pile (`1,577,128` points).

Key results:

- robust scanline q02–q98:
  `254.199721 source-units²`;
- changing longitudinal resolution from 80 to 320 bins changed that estimator
  by less than approximately `0.2%`;
- changing vertical boundary quantiles from q01–q99 through q05–q95 produced
  an approximately `9.26%` tested range;
- binary raster area was materially dependent on raster resolution;
- a marching-squares sub-cell contour produced almost the same area as the
  filled raster, showing that full boundary-cell counting was not the primary
  raster bias;
- a density-supported vertical-envelope family remained sensitive to both
  vertical resolution and density threshold, with approximately `9.98%`
  global tested range;
- low-ratio concave hulls showed strong cross-resolution stability
  (`~0.285–0.360%` for ratios `0.002–0.010` across the two tested raster
  resolutions), but hull tightness itself still materially changed the
  resulting area.

The experiments therefore narrowed the dominant scientific uncertainty to the
definition of the external gross pile boundary, rather than numerical
quadrature, longitudinal discretization, or pure depth protrusion.

No estimator has been promoted as authoritative. The next scientific decision
requires Campo Digital's same-pile manual/LiDAR360 reference area and,
preferably, the actual reference polygon.

Full experiment:
`docs/experiments/EXP-007-gs100g-boundary-estimator-comparison.md`

## 2026-08-25 — Front-depth visibility and structural-gap detection

Javier clarified that some visible spaces in the timber pile must not be
included in the measured face area.

Real GS100G diagnostics showed that immediate projection from `(u,v,z)` to
`(u,z)` can hide those openings because geometry farther behind the visible
face can occupy the same projected cells.

The measurement architecture was therefore refined:

```text
(u,v,z)
→ front-depth image
→ positive-depth recession candidates
→ front/rear visibility classification
→ (u,z)
→ projected face measurement
```

A reusable implementation was added in:

`src/lidar_volume/front_depth.py`

Synthetic tests cover:

- cavity detection with rear returns visible through the opening;
- gradual front-depth slopes;
- XY translation;
- XY rotation;
- point-order invariance;
- non-unit longitudinal axes;
- both transverse front orientations.

A floating-point grid-boundary defect discovered by the rotation-invariance
test was corrected with stable normalized grid indexing.

The reusable implementation was validated on the frozen real GS100G pile:

```text
input points              1,577,128
projected working points  1,535,717
valid front-depth cells     100,444
```

The known real cavity was automatically detected without using its location
during detection:

```text
surface scale 1.0 → rank #2
surface scale 2.0 → rank #3
surface scale 3.0 → rank #5
```

Observed geometry runtime:

```text
face frame       0.174 s
front-depth      0.330 s
three scales     0.088 s
combined         0.592 s
```

Front-depth/recession is integrated as an explicit opt-in diagnostic layer.

Candidate regions are not yet treated as confirmed physical voids, are not
subtracted from face area, and do not alter volume or measurement readiness.

Full technical record:

`docs/experiments/EXP-007-gs100g-boundary-estimator-comparison.md`


## 2026-08-25 — Reference validation and prelocalized measurement

Reference validation was separated from timber-stack localization after a
controlled run showed that applying the automatic pile locator again to an
already isolated GS100G pile retained only:

~~~text
input points             1,577,128
selected points          1,084,738
selected fraction           68.779%
~~~

That made the resulting face-area estimate unsuitable as a clean validation
baseline because localization and measurement error were mixed together.

An explicit prelocalized measurement mode was therefore added:

~~~text
--input-already-isolated
~~~

In this mode the pipeline records:

~~~text
localization_mode = prelocalized_input
~~~

and passes the complete input cloud directly to the face-measurement kernels
without claiming that automatic localization succeeded.

The frozen manually isolated real pile now gives:

~~~text
input / selected          1,577,128 / 1,577,128
selected fraction                 100.000%

longitudinal span             68.935522 source units
rectangle area               255.288370 source-units²
trapezoid area               254.199721 source-units²
projected raster area        284.250000 source-units²
raster vs scanline                11.162%
~~~

The scanline result reproduces the earlier frozen-cloud baseline. This
demonstrates reproducibility, not physical accuracy.

A separate face-area reference comparison contract was also added.

Comparison error metrics are generated only when:

~~~text
same pile explicitly confirmed
AND
estimate/reference area units compatible
~~~

Otherwise the reference is retained but comparison remains blocked. No
implicit conversion from source-coordinate units to square metres is allowed.

Face-area comparison remains independent from the existing volume-level
REFERENCE_VALIDATED readiness stage.

The front-depth diagnostic is now accessible through the measurement CLI:

~~~text
--front-side low_v
~~~

On the controlled real pile:

~~~text
front side                    low_v
recession candidates          35
front-depth runtime            0.338 s
recession runtime              0.028 s
~~~

The structural opening previously identified by the operator is independently
detected by the current default diagnostic as candidate #3:

~~~text
candidate area                0.8375 source-units²
median recession              1.0503 source units
maximum recession             1.9038 source units
recession score               0.9086 source-units³
~~~

The candidate remains diagnostic only. It is not treated as a confirmed
physical void, is not subtracted from face area, and does not affect volume or
readiness.

Remaining validation gates are:

- explicit CRS / physical-unit confirmation;
- same-pile LiDAR360 reference area or polygon;
- operational void inclusion/exclusion criterion;
- validation of automatic localization on the full point cloud;
- validation on additional timber piles;
- geometric-volume and commercial cubicación validation.

## 2026-08-26 — Shared face-estimator benchmark infrastructure (EXP-009)

The bilingual measurement console (with real LAS RGB propagated into the
point-cloud preview) and the measurement research roadmap / ADR-004 (shared
experiment architecture) merged to `main` as two separate, focused PRs.

Built the first implementation branch against that accepted architecture:
`src/lidar_volume/face_boundary.py` (shared closed-polygon validation and
measurement -- one function every estimator's area/perimeter goes through),
`face_estimators.py` (scanline, raster, and concave-hull adapters over one
shared `ProjectedFaceEvidence` bundle), `face_estimator_benchmark.py`
(orchestration, pairwise disagreement, gated reference comparison reusing
`face_area_reference.py` unchanged), the matching I/O pipeline and
`lidar benchmark-face-estimators` CLI command, and a persisted
`benchmark.json`/`summary.csv` artifact convention under
`reports/out/estimator-benchmark/<run-id>/` that the existing measurement-run
API/viewer glob cannot pick up.

Two of EXP-007's candidates -- sub-cell marching-squares and the
density-supported envelope -- were deliberately not reimplemented: EXP-007
already reached a negative/rejected conclusion for both, and no reusable code
or dependency (scikit-image) exists for marching squares. Selecting either
name raises a clear error pointing back to EXP-007 instead.

Running the new benchmark against the same frozen pile as EXP-008 reproduced
its scanline area (254.199721 source-units²) and raster-vs-scanline
disagreement (11.162%) exactly. Along the way, a real bug surfaced and was
fixed: converting a boolean raster mask into a measured polygon by unioning
per-row boxes fragmented on real data (24 disjoint parts, from 8-connectivity
diagonal touches that raster labeling treats as one component but that do not
share a union boundary as simple squares). `PolygonMeasurement` now carries an
explicit `part_count` and sums area/perimeter across parts rather than
silently keeping only the largest one.

The new concave-hull estimator (ratio=0.01, filled-mask boundary cells) gave
288.57 source-units² on the real pile -- in the same ballpark as, but not a
numeric match for, EXP-007's own low-ratio sweep (~268.5-274.3). This is
recorded as an open, plausible methodological difference (boundary-point
representation), not resolved by tuning the new code to match an
un-reproducible one-off script.
